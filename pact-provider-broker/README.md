# pact-provider-broker

The `orders-api` provider (`OrdersApi.java`), a Pact verification test, and a Docker Compose Pact Broker with a `curl` script for `can-i-deploy`.

## Goal
Verify the consumer pact against a real provider, then share pacts and verification results through a Pact Broker so it can answer `can-i-deploy`.

## Run it
```bash
mvn -q -B test                                   # provider verification from the pact file
docker compose up -d --wait && ./broker-flow.sh  # publish pact, publish result, can-i-deploy
docker compose down -v                           # remove the broker and its database
```
Expected: `OrdersApiProviderTest` verifies 2 interactions; `broker-flow.sh` ends with a `can-i-deploy: True - ...` line.

Not run end to end: neither command was run while writing this README. The Maven here has no Java 21, and Docker was not used, so the broker image `pactfoundation/pact-broker:2.113.0-pactbroker2.113.0` and `broker-flow.sh` are untested. The expected broker output above is what the script is written to print, not captured output.

`src/test/resources/pacts/orders-web-orders-api.json` is a copy of the file generated by `../pact-consumer`; refresh it after changing the consumer.

## What it proves
- `OrdersApi` (a JDK `HttpServer`) is started on a random port and must satisfy both interactions; the `@State` methods in `OrdersApiProviderTest.java` seed the data each state needs. Renaming `status` in the response would fail the test.
- `broker-flow.sh` shows the broker workflow over plain HTTP: PUT the pact for a consumer version, POST the verification result, query the matrix for `can-i-deploy`.
- `docker-compose.yml` pins Postgres 16.4 and the broker image, exposing the broker on port 9292.

## Trade-offs
- The script calls the broker API directly to avoid dependencies; real pipelines use the `pact-broker` CLI or the Maven/Gradle plugin.
- The pact is a file copy here; with a broker you would load it with `@PactBroker` and set `pact.verifier.publishResults=true`.
- The broker has no authentication and uses the compose-local password `pact-local-only`, so it is for local use only.

## When not to use it
- A few services with one deploy pipeline: contract bookkeeping costs more than it saves.
- Consumers you cannot identify or collect pacts from; use provider-driven contracts instead.
